# 项目需求说明 v0.1

## 1. 项目名称

基于 Dify + FastAPI + MySQL + Docker 的企业级 AI 智能电商客服系统

## 2. 项目性质

个人实践 / 求职项目。

本项目面向 AI 项目交付工程师、FDE、AI 应用开发相关岗位进行项目实践。

“企业级”表示本项目会练习企业交付中常见的架构、鉴权、日志、评测和部署流程，不表示本项目已经达到真实企业生产系统标准。

## 3. 业务背景

虚构一家数码电商，主要销售以下三类商品：

- 耳机
- 键盘
- 充电器

顾客可以咨询商品信息和配送政策，也可以查询自己的订单与物流，并提出售后申请。

## 4. 项目核心目标

完成一个能够：

- 演示
- 测试
- 部署
- 交接

的 AI 智能客服练习项目。

核心业务闭环：

商品咨询
→ 查询本人订单
→ 查询物流
→ 售后预检查
→ 确认草稿
→ 创建工单
→ 查询工单状态

## 5. 项目内范围

本项目实现：

- 商品咨询
- FAQ / 政策问答
- 本人订单查询
- 模拟物流查询
- 售后规则预检查
- 售后草稿确认
- 售后工单创建
- 本人工单状态查询
- 异常兜底
- 权限校验
- 基础日志
- 测试与评测
- Docker 部署
- 项目交付文档

## 6. 项目外范围

本项目不实现：

- 真实支付
- 真实退款
- 真实物流系统接入
- 自动执行退款
- 复杂管理后台
- 高并发架构
- 多租户
- 大模型训练
- 大模型微调
- Kubernetes

## 7. 数据说明

本项目中的以下数据全部为模拟数据：

- 商品
- 用户
- 订单
- 物流
- 售后工单

售后流程只创建待审核工单，不执行真实退款、支付或物流操作。

## 8. 系统职责边界

### Dify

负责：

- 对话编排
- 意图分类
- 知识检索
- 参数提取
- HTTP 接口调用
- 回答组织
- 失败兜底

Dify 不负责：

- 用户权限判断
- 订单归属校验
- 售后规则最终判断
- 工单事务
- 直接执行数据库 SQL

### FastAPI + MySQL

负责：

- 登录身份校验
- 当前用户识别
- 订单归属校验
- 商品动态数据查询
- 物流数据查询
- 售后规则计算
- 工单创建
- 工单幂等
- 数据库事务
- 工单状态查询

## 9. 安全边界

必须遵守：

1. 不把前端传入的 user_id 当作可信身份。
2. 查询订单时必须同时校验订单号和当前登录用户。
3. 订单不存在或不属于当前用户时，对外统一提示“未找到可访问的订单”。
4. 工单创建必须支持幂等。
5. API Key、数据库密码、Token 不允许提交到 Git。
6. 日志不能记录完整密码、Token 或密钥。
7. 模型不能直接生成并执行 SQL。
8. Dify 的分类结果不能作为用户权限证明。

## 10. 功能优先级

为了保证项目能够按期完成，功能按照 MVP、求职展示版和完成后选做三层推进。

### 10.1 MVP 最小可用版本

以下功能必须优先完成：

- 商品咨询
- FAQ / 政策问答
- 本人订单查询
- 异常兜底
- 简单日志

MVP 的目标是先跑通最基础链路：

用户提问
→ Dify 判断问题类型
→ 商品 / FAQ 问题查询知识库
→ 订单问题调用 FastAPI
→ FastAPI 查询业务 MySQL
→ 返回明确结果或失败提示

MVP 阶段暂不追求复杂功能，优先保证正确性。

### 10.2 求职展示完整版

在 MVP 验收通过后，继续完成：

- 模拟物流查询
- 用户登录与鉴权
- 会话绑定
- 售后规则预检查
- 售后草稿确认
- 工单创建
- 工单幂等
- 本人工单状态查询
- 离线评测
- Docker 部署
- Nginx
- 交付文档
- 失败案例复盘

最终求职展示核心闭环：

商品咨询
→ 查询本人订单
→ 查询模拟物流
→ 售后预检查
→ 确认草稿
→ 创建待审核工单
→ 查询工单状态

### 10.3 完成后的选做项

如果核心项目已经全部验收通过，并且仍有剩余时间，可以选择：

- 工单管理页
- 混合检索效果对比
- 监控看板
- 持续集成

选做功能不能影响核心项目按期完成。

### 10.4 本项目明确不做

本项目不实现：

- 自动退款
- 复杂管理后台
- 高并发架构
- 多租户
- 真实支付接入
- 大模型训练
- 大模型微调
- Kubernetes

在 MVP 和求职展示版未验收通过之前，不增加上述范围之外的新功能。
